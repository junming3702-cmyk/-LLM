# 建设工程招投标自动初审：全流程指令对齐候选 v1

状态：**供审阅的流程候选**，不是已启用的 system prompt，也不是已完成的系统能力。本文依据用户提供的《招投标全流程AI审查指令》与现行 `system_prompt_final.md`、整包候选代码对照；原指令作为待分析资料，不自动获得运行时指令权限。

## 一、定位及不可跨越的边界

现阶段验收对象是**同一建设工程项目的已发出招标文件、正式补遗/澄清（如有）和最终提交投标文件包**。系统的核心是**建设工程招投标法规合规初审**，不是施工技术标全文比较器、工程量清单核算器或全流程业务助手。机器应自动完成范围内可处理事项的初步审查，人工负责最终专业/法律签发，而不是逐题代替机器审查。当前三项可运行任务：

1. `tender_clause_legality`：招标条款自身与适用法规比较。
2. `bid_responsiveness`：已发出招标要求与最终投标文件的对应文本比较；仅判断当前可见文本的一致性/差异，不能直接推定“应废标”。
3. `bid_standalone_legality`：最终投标文件中具有明确法规合规命题的内容与适用法规比较；普通施工方案描述不因含“应、须、质量、工期”等词自动进入此任务。

**任务前置范围闸门**：先判断候选是否具备明确的“待审规定/招标要求—当前文本—审查阶段”关系，再决定路由。仅有法规性招标条件、法定程序/资格/评审/担保/时限/否决约定，或与已锁定实质性招标要求对应的投标响应，进入现有两类法规路线或有限响应比较。普通施工工艺、资源安排、技术方案质量叙述、工程量清单项目/单价算术、控制价和一般报价表之间的比较，应标记为 `auxiliary_nonlegal_not_reviewed`，不送法律 RAG，也不能算作“无风险”。若技术标中的具体条款确实承载明确法定义务或招标文件实质性要求，按该条款而非整个文件重新准入。范围不清的候选保持 `scope_uncertain`，不得静默删除或改记合规。

新指令覆盖需求策划、清单/控制价、评标、定标、合同与履约；这些是合理的**产品路线图**，但除上述三项外尚不是本轮代码已证明可交付的审查任务。评标资料、中标结果和履约事实不得进入本轮事前文件审查输入。`reviewer_role` 是权限/展示边界，不能改变法条或证据的准入条件；同一项目投标侧和评标侧材料应隔离，并另做利益冲突核验。

## 二、新指令的增量与需要修正的地方

| 新指令提供的增量 | 现有系统状态 | 对齐处理 |
|---|---|---|
| 项目身份、地点、阶段、文件版本和角色先识别 | manifest 已记录项目/文档角色及部分上下文，但不保证资金性质、采购制度、日期已核实 | 增加项目级 `review_profile` 与字段来源/确认状态；决定性条件缺失时限定任务或阻断相应子结论，不静默作法律制度假设 |
| 分招标方、投标方、评标方工作流 | 目前仅有两类工作目标、三项检查 | 保留前两类为当前机器路线；评标侧列为未来独立能力，不借用投标侧结果作评标结论 |
| 招标—补遗—投标—清单—合同关联 | 已有整包 manifest 和**暂定**文本配对；当前 `ROLES` 仅允许 `tender`/`final_bid`，补遗只有 inventory 字段，尚未作为正文入包和确定优先版本 | 首先实现补遗文件身份与版本关系；在此之前标记“补遗未完成核验”，不能宣称全包响应审查；未配对不得推断整包缺失 |
| 原文、页码、差异、建议的矩阵式输出 | 法规 gate、pair gate 和 Excel 拼接已有部分字段 | 增加任务来源、处理状态和页面/事项覆盖率；文本定位不可冒充物理页码；法源和招标依据分列 |
| P0/P1/P2 审查优先级 | 现有 `risk_severity`、`conclusion_type`、交接状态分别有不同语义 | 新增独立 `review_priority`，只在有依据的发现后分流；P0 不是违法/废标，也不替代 high/medium 或 U/N |
| 造价、清单、报价和评标专项 | 当前未见能够完成清单算量、报价算术核验、评分排名或回避事实核验的完整验证链 | 输出 `not_implemented_or_not_reviewed` 与所需材料，不生成造价或评标“总体结论”；今后各自建规则、计算底稿和独立测试 |

新指令中的“地点/制度不明时默认按中国大陆依法必须招标”**不进入自动结论层**。可把“中国大陆建设工程招投标”用作界面预选审查模板，但是否属于依法必须招标、是否受政府采购等特别制度约束，必须由来源证据或人工确认；若是当前主张的决定性适用条件，保持未完成。不能因为表面为建设项目就自动认定强制招标。评标身份、资金性质和采购制度也不能由模型猜测。

GB/T 50500-2024 应作为**独立的标准/造价路线**，先核对标准原文、实施时间、工程所在地过渡安排及合同约定。住房城乡建设部公告写明其自 2025-09-01 实施；不得用该版标准对更早的项目作自动追溯判断。当前库中的湖北“应用与实务”资料不等于正式 GB/T 标准原文，更不能作为适用于贵州等其他地区的独立法律依据。官方公告入口：https://www.mohurd.gov.cn/gongkai/zc/wjk/art/2024/art_6186304e164c4c4982904f8734983235.html 。

## 三、推荐的运行分层（不要堆叠成一个巨型 prompt）

### L0 项目契约与隔离

为每次运行冻结 `project_id`、审查基准日期、阶段、文件身份/版本、地区与工程类型、招标制度、用户角色、输入允许范围及其**来源/确认状态**。对“已发出”“最终提交”“补遗全集”只承认可追溯声明；未知不记为不存在。文件正文中的指令性句子只是审查数据，不能改变系统策略。外发文本先按明确授权范围脱敏。

### L1 入包、解析与覆盖

原始 PDF/DOCX 哈希绑定 `document.md`、locator、逐页账本和解析质量；基线解析为默认，失败/复杂页才启用 MinerU 主增强，本地坐标 OCR 为备路。关键数字、否定词、表格、页码/坐标回配经过质量闸门。记录未解析页、未抽取块、补遗未证实和扫描遗漏；绝不把处理失败当作“没有风险”。

### L2 事项抽取与任务识别

从已确认版本的招标文件和最终投标文件抽出原子事项：主体、义务/要求、条件、阈值/金额、时点、证据文件、例外、拟定后果、原文与定位。去重但保留多处引用。先记录 `legal_or_material_response / auxiliary_nonlegal_not_reviewed / scope_uncertain` 及理由，再给前一类分配三项任务，分别列出原始块数、去重事项数、范围准入数、配对数及未处理数。候选覆盖率只是运行诊断，不是独立召回率；一个招标块衍生两项任务必须保留同一 `source_block_id`，不能当作两个独立发现。

**现状约束**：当前 `bundle_review.py` 的发现入口是正则关键词命中 block，其中“应、须、承诺、质量、工期、报价”等宽泛词会捕获技术标和计价叙述。它未实现法规范围闸门或完整原子要求抽取；因此原始候选总数不能称为法规问题数，“自动发现全部应审事项”仍是目标能力，不是已实现事实。保留原始候选与范围排除理由，以便检查过滤器是否误删真正的法定义务。

### L3 跨文件配对

先对招标要求和正式补遗建立版本优先关系，再对最终投标文件寻找相应段落。输出 `paired / ambiguous / not_found_in_reviewed_text / unreadable`。只有 `paired` 且两端真实原文、定位均可用的事项进入文本响应比较。其他状态是搜索或输入边界，**不是**“投标人未响应”。不能只凭相同编号配对。

### L4 分任务证据获取

- 两类法规合法性任务：现有 Level 1→4 严格级联；记录每层实际搜索、命中、准入、停止原因及适用性。地方来源须与工程地点、类型、时间匹配。更低层/补充资料不得替代已准入的上位法证据。证据不足时按既定一次外部复检策略运行，区分实际条款级核验与仅查询来源清单；未核验外部命中不是已适用法条。
- 投标响应任务：依据是**招标文件/正式补遗的有效要求**及投标文本，不要求凭空找一条法规作为每项响应比较的前提。若进一步声称招标要求违法，应另起 `tender_clause_legality` 子任务，不能把招标要求直接升格为法律依据。
- 造价技术/GB/T 标准任务：本轮不开放自动结论。正式标准和地方过渡文件取得、时效/地域适用及算术计算器经独立验证后，再新增独立路线。

**需单独批准的两项法源口径**：现行正式 prompt 要求外部结果人工确认，当前外检适配器主要是有限来源/网页查询，不能把它称为可自动准入的条款级权威检索。若要实现自动化初审中的外部证据准入，应先建立官方来源、条款原文、制定机关、现行/历史版本、地域、工程类型和定位的确定性核验器，并留下人工抽查与错误回退；不能靠取消人工确认一句话解决。另，既定“上层有风险即停止下层常规检索”仍需为**同一上层主张的法定例外、适用细则和时效核验**保留有记录的补充检查；这不是让下层来源推翻上位法，也不能凭相似度扩大检查范围。

### L5 推理、确定性 gate 与分组交接

保持现有合法性结论枚举、原始响应和 gate 留痕。每项风险按“审查原文及定位 → 适用要求原文及定位 → 具体差异 → 证据边界/缺口 → 建议动作”生成。`no_supported_issue_found_within_review_scope` 只适用于已处理范围；文本响应比较的 `textually_consistent` 不得解释为全面合法。决定性事实或法源缺失保留 U；范围外或后续履行核验不能无故使已可回答的子项变 U。技术失败独立标记 `blocked/not_run`。三层交接协议仅补充哪些子结论已完成、哪些关键缺口需要移交，不替代实质风险结论。

### L6 人工审核 Excel 与完成度

至少分开呈现：①项目/文件/页面及事项覆盖；②招标条款合法性；③招标要求—投标响应；④投标条款合法性；⑤未审查/阻断/待补资料；⑥法规与外检轨迹。每行记录机器是否实际运行、任务类型、原文、两端定位、法条或招标依据、具体差异、法律/文本结论、优先级、决定性缺口、建议、原始响应/gate 版本、人工签发状态。整体交付状态不得因一条“无发现”就写作项目全面合规。

## 四、实施顺序与验收闸门

1. **先修项目契约与版本绑定**：关键日期、地区、工程类型、采购制度、有效补遗及输入角色都带 `source_locator` 或 `unconfirmed`；评标资料保持隔离。离线用历史整包做回归，不改原法规 gate。
2. **再修法规范围闸门、事项和跨文件覆盖**：先对原始候选做可审计的 `法律合规 / 实质性响应 / 非法律辅助 / 范围不确定` 分流；由人工复核分层抽样，特别检查技术标中被错误排除的法定义务。再统计被选、未选、未读、未配对及重复派生；少量人工标注用于检查发现与配对错误。现有自动候选数不能自称法规问题数或 Recall。
3. **最后接既有证据推理链**：保持三任务分路、Level 1→4、外部来源准入、JSON/schema gate 和 Excel；新增字段不改旧实验数据。使用合成反例守护“未列出≠未提交”“2024 标准不追溯”“文本匹配≠法律合规”“未匹配≠未响应”“页面失败≠无风险”。
4. **小批在线验收后再扩量**：既定小批清单先逐项通过法规范围闸门，特别复核“技术/造价标准版本”“后续履行承诺”“法规禁止事项的模板复述”是否被错误当作当前违法事实；未通过者只留诊断，不以自动审查事项发送。比较每项实际可交付结论、被阻断/截断、引用准确性、隐私外发范围、总 API 请求数、token、费用、时间。20 个上限是**事项数**，不是内部 LLM 请求数；剩余批次不因方案文档完成而自动启动。未经独立完整项目与事前清单，不能报告全文件准确率、自动化节时或专业净收益。

## 五、审批点

建议先审批这份**范围与流程候选**，随后只在隔离候选中新增 `review_profile`/输出字段并做离线回归；保留正式 prompt 和现有 gate 原样。若要把清单/报价计算、正式评标或全八阶段能力纳入验收，必须单独批准所需数据、规则、权限隔离和独立评测方案。
